# ML path: demoted to an offline tool (D17, KAN-35)

**Decided 2026-09-27 by the operator.** Rubric: architecture — what the running
system should contain — not the promotion pipeline.

## Decision

**Demote.** `ml-model` and `signal-generation` leave the running stack.
`scripts/run_paper.py` is the only recommendation source, as it has been in
practice all along.

Demote is not delete. The operator's intent is to **train ML models and test
them offline before anything is integrated** into the working system, so the
training and registry code is kept as the tool for doing exactly that:

| Kept, offline | Removed from the live system |
|---|---|
| `services/ml_model/` (trainer, registry, predictor, feature assembly, regime, runner) and its tests | `ml-model` and `signal-generation` from `docker-compose.yml` |
| `services/signal_generation/` and its tests | `risk-management`'s `depends_on: ml-model` |
| `scripts/train_signal_model.py`, `scripts/retrain_model.py` | their Prometheus scrape jobs, their names in `ServiceMetricsEndpointDown`, the observability overlay's `depends_on` |
| `research/` | their Dependabot docker entries (nothing builds those images) |
| `model_versions` table and the content-hash integrity check | `ml_model.retrain_cadence_months` (no reader, no scheduler) |

## Inputs

**Is the daily path intentionally model-free, or was an active model expected?**
Model-free, in practice and now by decision. `model_versions` has 0 rows, so
there has never been an active model to load.

- **Nothing consumed the service path's output.** `signal-generation` published
  only to `stream:signals`; its only consumer was `ml-model`. Every entry on
  `stream:recommendations` came from `run_paper.py`
  (`docs/operations/live-topology.md`, measured 2026-09-04).
- **Both containers were "healthy" and useless.** In the week to 2026-09-25
  `ml-model` logged no events at all and `signal-generation` logged ~376,000
  `signal_compute_error` lines. The heartbeat healthcheck proves only that the
  loop turns.
- **The three pieces broken at spec time (2026-08-13):** scikit-learn missing
  from the lockfiles, the native-LightGBM vs `joblib` format mismatch, and the
  retrainer never setting `content_hash`. All three have since been fixed
  (loader round-trip test, 2026-09-04; sklearn declared in `pyproject.toml`), so
  **offline training works today** — which is what makes demotion cheap rather
  than lossy.
- **No scheduler.** `retrain_cadence_months` had no reader anywhere and no
  launchd unit. A config key nothing reads is a claim the system does not keep,
  so it is removed. Retraining is an operator-run step.

## What integration requires later

A model enters the running system only after offline evaluation says it earns
its place — and then through the promotion pipeline in
`docs/designs/project-direction.md`, like any strategy. Re-wiring is then:
restore the compose services from this commit's parent (or, better, feed a
promoted model into `run_paper.py` directly rather than reviving a parallel
producer), re-add scrape jobs and alert coverage, and add a real scheduler if
retraining is to be periodic.

## Operator step after deploy

Removing a service from compose does not stop its running container. After
promotion and deploy, `docker compose -p algo-poc ps` still shows the two as
orphans until they are stopped — e.g. `docker compose -p algo-poc up -d
--remove-orphans` from the deploy clone, or `docker stop` on the two
containers. Neither holds state (no volumes; Redis entries on `stream:signals`
are unused).
